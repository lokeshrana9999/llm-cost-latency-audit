# LLM usage audit (proof of format)

No case study yet, so the first audit is free.

This folder shows exactly what the free 48-hour audit produces: a markdown report
built from a model / token / timing export. Everything in `sample_export.csv` and
`sample_report.md` is SYNTHETIC, generated by a seeded script. It shows the
format of the output, not results from any real system.

## What the report contains

- Spend by model (input, cached input, output) using `prices.json`
- Cost per task and per successful task
- p50 / p95 latency and time-to-first-token by model
- Token distribution, share of spend from input tokens, and spend on repeated
  long prefixes (if a `prefix_hash` column exists)
- A ranked list of opportunities, each a hypothesis to test with evals, with
  the arithmetic shown and labeled WHAT-IF. Never a promised saving.

## Export columns (CSV or JSONL, one row per model call)

Required: `model`, `input_tokens`, `output_tokens`, `latency_ms`.
Optional: `timestamp`, `cached_input_tokens`, `ttft_ms`, `task_id` or
`session_id`, `success` (true/false), `prefix_hash`, `prefix_tokens`.
Common aliases (`prompt_tokens`, `completion_tokens`, ...) are accepted.
`input_tokens` is assumed to include cached tokens; otherwise pass
`--input-excludes-cached`.

## Run it (Python 3.8+, stdlib only)

```
python make_sample.py
python audit.py sample_export.csv -o sample_report.md
```

For your own data: `python audit.py your_export.csv -o report.md`.

## What the audit does NOT need

No prompts, no completions, no user content, no API keys. Only counts, model
names, timings and (optionally) an opaque hash of the shared prompt prefix.

## Prices

`prices.json` is dated 2026-11-11 and is UNVERIFIED. Check every number
against the provider's pricing page and edit the file before relying on any
dollar figure. Cache-write premiums and batch discounts are not modelled.

## How a paid pilot extends this

1. Evals on real traffic: a small graded set per route, so every hypothesis
   above is tested rather than assumed.
2. One or two optimizations (for example caching or routing), shipped
   behind the eval results.
3. A CI regression gate: the eval set runs on prompt or model changes and
   blocks changes that lose quality or raise cost per successful task.
